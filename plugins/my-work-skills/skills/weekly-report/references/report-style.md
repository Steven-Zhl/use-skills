# 周报风格规范

周报只回答「做了什么、有什么用处」，不解释「怎么做的」。**每一条控制在 50 字以内**，写不下就是写了多余细节。

## 分类规则

| 类型 | 处理方式 | 判断标准 |
|---|---|---|
| 功能性更新 | **单独成条** | 做出了用户可感知的新能力 |
| 大幅更新 / 重构 | **单独成条**，只写问题和结果 | 动了模块边界、职责划分、数据结构、跨端协议 |
| 优化 / 调整 / 改名 / Bug 修复 | **合并成一条**，每个改动一句话带过 | 单点改动小，拆开会让周报变成流水账 |

零散小改动一律并进合并条，不要为了看起来充实而拆条。几个小改动合成一点时，每个只说做了什么、省掉原因和过程。

## 单条写法

- **一条一个主题，50 字以内**。超出时先删修饰语和实现细节，再考虑拆条。
- **只讲结果，不讲实现**：不写文件名、函数名、接口名、字段名，也不写判定流程、校验顺序、加锁位置、数据结构设计这类步骤。读者要知道能力，不需要知道代码长什么样。
- **重构条目只写两句**：原来卡在哪、现在怎么解决。省掉「三级策略」「逐级回溯」这类机制描述。
- **合并条用分号串联**，每个分句一个动作加一个结果，不分点展开。
- 动词开头读起来最顺：「实现…」「改为…」「支持…」「避免…」。

## 详略对照

| 写法 | 问题 |
|---|---|
| 路径权限与沙盒共用同一套三级策略（可写、只读、拒绝），符号链接按真实路径判定、新建路径逐级回溯校验，防止越界；同一文件的修改在锁内完成并在前后比对文件状态，避免并发覆盖；单文件大小与单次输出量均设上限。 | 太细，读者要读两遍才能提取出三件事 |
| 路径权限与沙盒共用权限配置，排除符号链接、相对路径等越界情况；文件修改加并发锁；工具层限制单文件大小与输出量。 | 合适：三件事一眼看清，机制细节省掉 |
| 原来解析、目录操作、安装逻辑混在一个文件里，且各自维护一套校验规则，改一处容易漏改另一处；本次按职责拆成三个模块，校验规则收敛到一处。 | 合适：问题一句、结果一句 |

## 模板

```markdown
# 周报（YYYY-MM-DD ~ YYYY-MM-DD）

## 功能与更新

1. **<功能名>**：<做了什么、能干什么>。
2. **<模块名>调整**：原来<卡在哪>，本次<怎么改>，<达成什么>。

## 优化与修复

3. **<模块/场景>优化**：<要点一>；<要点二>。
4. **工具与界面调整**：修复弹窗高度异常；统一按钮文案；清理未使用的依赖。
```

## 常见退化与纠正

| 退化写法 | 问题 | 纠正 |
|---|---|---|
| 照抄提交消息 | 泛词提交会让周报空洞 | 读 diff 还原实际内容 |
| 一条写两三行，讲清每个步骤 | 读者拿不到重点，周报变成技术文档 | 删到 50 字以内，只留做了什么和有什么用 |
| 小改动逐条单列 | 流水账，稀释了真正的重点 | 合并成一点，各自一句话 |
| 「优化了若干代码，提升了可维护性」 | 空话 | 写具体解决了什么痛点 |
| 一条里塞 5 个互不相关的大功能 | 掩盖工作量与重点 | 大功能拆开，小调整合并 |
| 把技术选型、调试过程写进正文 | 不是周报该有的内容 | 正文只留结果，过程放对话里说明 |
