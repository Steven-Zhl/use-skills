# 周报风格规范

## 分类规则

| 类型 | 处理方式 | 判断标准 |
|---|---|---|
| 功能性更新 | **单独成条** | 做出了用户可感知的新能力 |
| 大幅重构 | **单独成条**，且必须交代架构问题 | 动了模块边界、职责划分、数据结构、跨端协议 |
| 优化 / 调整 / 改名 / Bug 修复 | **合并成条**，一条里塞多个要点 | 单点改动小，拆开会让周报变成流水账 |

小功能与重构混在一起的提交，按上述规则拆开，不要跟随提交的粒度。

## 单条写法

- **一条一个主题，控制在 50 字左右**，可直接读、不绕弯。
- **只讲功能与结果，不讲技术细节**：不写文件名、函数名、接口名、字段名、参数名。必要时用「模块」「链路」「数据结构」这类中性词。
- **重构条目写清三件事**：原来什么样的结构 → 导致了什么问题 → 现在怎么解决。问题要落到实际痛点上（重复实现、容易不一致、无法并发、前端必须持有多余标识才能操作等），不要写「提升了可维护性」这类空话。
- **合并条用分号串联要点**，每个要点一个短句，前半句做动作、后半句说效果。
- 动词开头的短句读起来最顺：「实现…」「改为…」「支持…」「避免…」。

## 模板

```markdown
# 周报（YYYY-MM-DD ~ YYYY-MM-DD）

## 功能与重构

1. **<功能名>**：<做了什么、能干什么>。
2. **<模块名>架构重构**：原来<旧结构的毛病>，导致<具体问题>。本次<怎么改>，<达成什么>。
3. ...

## 优化与修复

4. **<模块/场景>优化**：<要点一>；<要点二>；<要点三>。
5. **工具与界面调整**：<要点一>；<要点二>；...（零散小改动都归到这里）

---

> 备注：<未提交改动的提交计划、需要用户处理的遗留问题>。
```

## 常见退化与纠正

| 退化写法 | 问题 | 纠正 |
|---|---|---|
| 照抄提交消息 | 泛词提交会让周报空洞 | 读 diff 还原实际内容 |
| 「重构了 skill 模块，拆分为 info/dir/file」 | 技术细节堆砌，看不出价值 | 「原来解析、目录操作、安装逻辑混在一起，且两套校验规则容易不一致，本次按职责拆分并统一规则」 |
| 「优化了若干代码，提升了可维护性」 | 空话 | 写具体解决了什么痛点 |
| 一条里塞 5 个互不相关的大功能 | 掩盖工作量与重点 | 大功能拆开，小调整合并 |
| 把技术选型、调试过程写进正文 | 不是周报该有的内容 | 正文只留结果，过程放对话里说明 |
