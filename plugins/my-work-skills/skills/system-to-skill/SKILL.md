# 内部系统 → 办公助手 Skill 生成流程

目标：读一个陌生的内部系统仓库，产出一个**给办公助手用的 Skill**（SKILL.md + 调用脚本 + 按需参考资料），让普通员工用自然语言完成日常业务。

## 核心原则（贯穿全程，违反即返工）

1. **读者是办公助手，不是开发者。** 最终 Skill 里不出现：源码路径/行号、类名、技术栈、表结构、内部包名。这些只能写进 `dev-notes.md`。
2. **按"用户要办的事"组织，不按"系统有哪些接口"组织。** 一个脚本 = 一个用户意图，可能在内部串联多个接口。
3. **助手不拼 HTTP 请求。** 鉴权、分页、多接口编排、字段裁剪、枚举翻译、错误翻译，全部封装在脚本里。脚本入参是业务语言（`--order-no`），出参是精简、已翻译的 JSON。
4. **宁少勿滥。** 一个系统通常只有约 20% 的功能适合办公助手。目标 10~20 个高频场景，管理后台、配置维护、字典维护、批量导入导出默认排除。
5. **代码读不出的业务规则不要猜。** 记入 `02-open-questions.md`，交给系统维护者确认。
6. **人工闸门不可跳过。** 阶段 1 的场景清单必须经用户确认后，才能进入阶段 2。

## 工作目录约定

```
skill-build/<system-name>/
├── 00-context.md          # 阶段0：输入信息
├── 01-scenarios.md        # 阶段1：场景清单（供人审核）
├── 02-open-questions.md   # 阶段1：需向维护者确认的问题
├── dev-notes.md           # 开发者信息（代码位置、技术栈、接口清单），不进最终 Skill
└── skill/<system-name>/   # 阶段2：最终 Skill（可直接分发）
    ├── SKILL.md
    ├── scripts/
    └── references/
```

## 阶段 0：确认输入

先向用户确认下列信息，缺失的直接询问，不要臆测。模板见 `assets/context.md.tpl`。

- 系统名称、仓库路径、面向的员工角色（业务员/财务/仓管/管理层…）
- 可用于验证的**测试环境**地址与调用方式（注意：不得对生产环境执行写操作）
- 目标助手的脚本运行环境（Python 版本、可用依赖、是否有网络限制）
- **鉴权方式**：助手如何拿到用户身份/token（环境变量？SSO？固定服务账号？）。这决定 `_client.py` 怎么写，也决定权限是否按用户隔离。
- 已有的接口文档/业务文档/维护人联系方式（有则优先读）

## 阶段 1：探索并产出场景清单（不写任何 Skill 文件）

### 1.1 探索方法

**从用户视角入手，而不是从 Controller 入手：**

1. 先看前端：菜单/路由/页面/按钮/表单 → 得到"用户在系统里能做什么"。
2. 再看后端：页面调用了哪些接口 → 得到场景与接口的对应关系。
3. 再看业务规则：状态枚举与流转、权限点/角色、校验逻辑、审批流配置、金额/数量阈值。
4. 顺手记录副产物到 `dev-notes.md`（代码位置、技术栈、接口清单）。

### 1.2 场景筛选

保留：员工日常高频、有明确输入输出、能用一句话描述的任务（查询进度、查待办、提交申请、审批、查询单据详情）。
排除：管理后台配置、数据字典/权限维护、报表导出、批量导入、需要复杂表单/文件上传交互的操作（除非高频，且单独标注"需人工介入"）。

### 1.3 输出

- `01-scenarios.md`：按 `references/scenario-template.md` 格式，每个场景包含用户口语化例句、涉及的接口（**仅在 dev-notes 中给出代码位置**）、前置条件、状态限制、权限、读/写与风险等级。
- `02-open-questions.md`：代码里读不出、需要维护者回答的问题（阈值、例外规则、特殊状态含义等）。
- 末尾给出**推荐纳入 / 推荐排除**的清单及理由，方便用户裁剪。

### ⛔ 闸门

输出以上文件后**停止**，向用户汇报：场景数量、推荐纳入项、最需要确认的 3~5 个问题。等用户回复确认或裁剪后再进入阶段 2。

## 阶段 2：生成 Skill

只针对用户确认的场景生成。严格遵循：

- `references/skill-output-spec.md`：最终 Skill 的结构、SKILL.md 写法、description 写法、references 拆分规则。
- `references/script-conventions.md`：脚本的输入/输出约定、错误处理、写操作安全机制。
- 脚手架：`assets/_client.py.tpl`（公共客户端）、`assets/script.py.tpl`（单场景脚本）、`assets/SKILL.md.tpl`（目标 SKILL.md 骨架）。

要点速记：

- 一个系统一个 Skill，`name` 用系统名，`description` 写清触发关键词。
- SKILL.md 控制在 150 行内；状态机/术语表/FAQ 放 `references/`，并在 SKILL.md 里写明何时读。
- 所有写操作脚本：默认 dry-run，必须 `--confirm` 才真正执行；SKILL.md 里明确"先向用户确认参数再执行"。
- 枚举值、状态码、内部 ID 一律在脚本里翻译成业务语言，脚本输出不含无用字段。

## 阶段 3：验证

1. **跑脚本**：在测试环境逐个运行只读脚本，写操作脚本先 `--dry-run`；只有在用户明确允许的测试环境才做真实写入。将真实输出记入 `skill/<name>/references/` 之外的 `03-verification.md`（含命令、输出摘要、失败项）。
2. **写测试话术**：为每个场景写 3~5 句员工真实会说的话（含模糊表达、缺参数、口语化），存为 `evals/prompts.md`，供后续用助手实测触发与选脚本是否正确。
3. **自检**：逐项过 `references/quality-checklist.md`，不通过则修改后重检。

## 阶段 4：交付

向用户汇报（简明，不重复文件内容）：

- 生成的 Skill 路径、覆盖的场景数、已验证/未验证项
- 明确**未覆盖**的功能及原因
- 仍未解决的待确认问题（指向 `02-open-questions.md`）
- 建议的下一步：用 `evals/prompts.md` 在真实助手中跑一遍

## 常见错误做法

| 错误 | 正确 |
|---|---|
| 输出成 Swagger 式"接口 → 参数 → 返回值"文档 | 输出"场景 → 脚本 → 业务规则" |
| 在 SKILL.md 写源码位置、技术栈 | 放 `dev-notes.md`，不进最终 Skill |
| 让助手自己 `curl` 拼请求 | 封装脚本，助手只传业务参数 |
| 一个接口一个脚本 | 一个用户意图一个脚本，内部串联多接口 |
| 脚本原样返回 80 字段 JSON | 裁剪为 5~10 个关键字段并翻译枚举 |
| 覆盖系统所有功能 | 只做 10~20 个高频场景 |
| 猜测业务规则（阈值、例外） | 写入待确认问题 |
| 没等用户确认场景清单就写 Skill | 阶段 1 后必须停下 |
| 在生产环境测试写操作 | 只用测试环境 + dry-run |
