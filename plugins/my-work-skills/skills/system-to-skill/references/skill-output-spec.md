# 最终 Skill 的结构与写法规范

## 目录

```
<system-name>/
├── SKILL.md
├── scripts/
│   ├── _client.py              # 公共：鉴权、base_url、重试、错误翻译、输出
│   └── <verb_noun>.py          # 一个脚本 = 一个用户意图
└── references/                 # 按需加载，不常驻上下文
    ├── glossary.md             # 业务术语、状态码 → 含义
    ├── status-flow.md          # 单据状态流转、各状态下可执行操作
    ├── rules.md                # 业务规则（阈值、审批条件、例外）
    └── faq-pitfalls.md         # 常见失败原因与处理
```
references 只在确有内容时创建，不要为凑结构建空文件。

## SKILL.md 规范

**frontmatter**
- `name`：系统名，小写连字符。
- `description`：一段话，包含「能做什么」+「什么时候用」+ 触发关键词（用户口语中会出现的词：运单、发运、订舱、待审批……）。写得略"主动"，避免助手漏触发。同时可写"不适用于…"以减少误触发。

**正文结构（≤150 行）**
1. 使用前须知（鉴权、输出格式、写操作规则）
2. 能力清单表：`用户想做什么 | 脚本与示例命令 | 备注`
3. 典型流程（2~4 个最高频场景：缺参数如何问、调用什么、如何向用户转述）
4. 关键业务规则（只放会影响助手决策的，每条一句）
5. 常见错误与处理（错误码 → 该怎么做）
6. 何时读 references（"遇到 X 情况时读 references/xxx.md"）

**禁止出现**：源码路径、类名、技术栈、表结构、完整接口 URL、鉴权头拼接方式、原始 JSON 字段说明。

## 写法要点

- 用祈使句和具体命令，不写背景介绍。
- 告诉助手**如何向用户转述**：概括为自然语言，不要贴 JSON。
- 告诉助手**何时该停下问用户**：缺参数、多个候选、写操作前。
- 告诉助手**何时不该重试**：权限错误、状态不允许。
- 业务规则每条都能追溯到代码或维护者确认；无法确认的不写，或标注"待确认"。

## references 拆分规则

- 内容只在部分场景才用到 → 放 references，SKILL.md 只写一句触发条件。
- 超过 100 行的文件顶部加目录。
- 状态码/枚举对照表放 glossary，脚本里也要有同样的映射（以脚本为准，glossary 供助手解释用）。
