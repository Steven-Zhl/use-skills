# 脚本约定

## 基本要求

- 语言：默认 Python 3，仅用标准库 + `requests`（除非阶段 0 确认了其他环境）。
- 命名：`动词_名词.py`（`query_shipment.py`、`list_pending_approvals.py`）。
- 每个脚本头部 docstring 写：用途（业务语言）、参数、示例输出。
- 支持 `--help`，参数说明用中文业务语言。
- 公共逻辑统一放 `_client.py`，不在各脚本重复。

## 入参

- 用业务语言命名：`--order-no`、`--start-date`，不是 `--projectId`。
- 用户可能给出不同形式的标识（订单号/运单号/柜号）→ 脚本内部尝试识别，或提供 `--kind` 参数。
- 日期统一 `YYYY-MM-DD`；分页用 `--limit`（默认 10~20）。
- 用户身份取自鉴权凭据，不让助手传"当前用户 ID"。

## 出参（stdout，UTF-8 JSON）

成功：
```json
{"ok": true, "data": {...}, "summary": "一句话概括（可选）", "hint": "给助手的下一步建议（可选）"}
```
失败：
```json
{"ok": false, "error_code": "NOT_FOUND", "message": "未找到该单号", "suggestion": "请确认是订单号还是运单号，或提供项目名称"}
```
- 失败时退出码非 0，但仍然输出上面的 JSON 到 stdout。
- 不输出堆栈、HTTP 原文、内部 URL、token。日志走 stderr 且默认静默。

## 数据整形

- 只保留助手回答问题需要的 5~10 个字段；其余丢弃。
- 枚举值、状态码翻译为业务语言；保留原码仅当助手确需时。
- 内部 ID（主键）不外露，除非后续脚本要用（此时字段命名为 `ref`，并在 SKILL.md 说明）。
- 时间转为本地可读格式；金额带币种。
- 列表结果附 `total` 和 `truncated`（是否被 limit 截断）。
- 结果为空时返回 `ok: true` + 空列表 + `hint`，而不是报错。

## 多接口编排

一个场景需要多个接口时，全部在脚本内完成（定位 → 取详情 → 取状态），失败要指出是哪一步（用业务语言）。不要把中间步骤暴露成让助手串联的多个脚本，除非中间需要用户选择。

## 写操作安全（必须）

- 默认只做 dry-run：校验参数、调用只读接口检查前置条件（状态是否允许、权限），返回"将要执行的内容"。
- 传入 `--confirm` 才真正提交。
- 高风险操作（撤销、删除、审批通过、金额相关）在 SKILL.md 中标注 ⚠，要求助手先向用户复述关键参数并得到明确同意。
- 尽量幂等：重复提交前先检查是否已存在，存在则返回已存在的单据。
- 不提供删除类脚本，除非用户在阶段 1 明确要求。

## 错误处理

`_client.py` 统一把 HTTP 状态/业务错误码映射为 `error_code` + 中文 `message` + `suggestion`：

| 类别 | error_code | 助手应当 |
|---|---|---|
| 鉴权失效 | AUTH_EXPIRED | 告知用户重新登录，不重试 |
| 无权限 | FORBIDDEN | 告知用户联系相关负责人，不重试 |
| 未找到 | NOT_FOUND | 请用户核对标识 |
| 参数不合法 | INVALID_INPUT | 按 suggestion 向用户补充信息 |
| 状态不允许 | STATE_CONFLICT | 解释当前状态，指向 references/status-flow.md |
| 系统异常/超时 | UPSTREAM_ERROR | 可重试一次，仍失败则告知用户稍后再试 |

系统特有的业务错误码映射，在阶段 1 从代码中收集，写入 `_client.py` 的 `ERROR_MAP`。

## 凭据

- 从环境变量读取（`<SYS>_BASE_URL`、`<SYS>_TOKEN`），或按阶段 0 确认的方式获取。
- 严禁将凭据、内部真实地址、测试账号写入 Skill 文件。
