# 变更收集与可信度判断

## 收集提交清单

```bash
# 提交清单（本周）：hash | 时间 | 作者 | 消息
git log --since="YYYY-MM-DD 00:00" --until="YYYY-MM-DD 00:00" \
  --pretty=format:'%h|%ad|%an|%s' --date=format:'%m-%d %H:%M'

# 确认是否漏掉其他分支的提交
git log --all --since="..." --pretty=format:'%h|%ad|%d|%s'

# 每条提交的规模与文件清单
git show --stat --format='%h %s' <hash>

# 完整提交消息（含 body，有些信息只在 body 里）
git log -1 --format='%B' <hash>
```

`--since` 用本地时区，跨时区协作时向用户确认口径。

## 判断清单：哪些提交必须读 diff

按「消息能覆盖的改动范围」与「实际改动范围」比对，命中任一条即读 diff：

| 特征 | 说明 |
|---|---|
| 消息是泛词 | `其他优化`、`一些调整`、`改名`、`杂项`、`updates`、`fix bug`、单字消息 |
| 文件数多但消息短 | 十几二十个文件、几百行改动，消息只有一行字 |
| 消息与文件不匹配 | 消息说打包配置，diff 里出现业务代码、接口文档、删除文件 |
| 出现未提及的成簇改动 | 新增文档、批量删除、依赖清单变更等，通常在消息里只字未提 |
| 消息含多个动词 | 一条提交干了多件事，需要拆开看是否该拆分汇报 |

反之，消息具体且文件范围吻合的提交（如「修复多个审批弹窗高度异常」+ 两个弹窗文件）可以快速核对 `--stat` 后略过。

## 读 diff 的取巧方式

不必通读全文，按下面顺序抓主题：

```bash
# 新增/删除的文件名，一眼看出功能模块
git show --stat --format='' <hash> | cat

# 只看新增注释与 docstring：作者往往在这里写清了意图
git show <hash> | grep -E '^\+' | grep -E '^\+ *(\*|//|/\*\*)' | head -60

# 抓命名变更（识别"改名"类提交的真实范围）
git show <hash> -U0 | grep -E '^[-+]' | grep -vE '^(\+\+\+|---)'

# 抓跨进程协议、导出接口的变化
git show <hash> -- <关键文件> | grep -E '^[-+]' | grep -E 'export|invoke|handle'
```

删除量远大于新增量的提交要留意：可能是清理误提交文件、迁移旧实现，这类内容通常值得记一句，但要区分「真实工作量」与「清理仓库噪声」。

## 收集未提交变更

```bash
git status --short --branch            # 先看全貌与分支同步状态
git diff --stat && git diff            # 工作区
git diff --cached --stat               # 暂存区
```

未提交改动通常天然按主题分组（同一功能的多个文件一起改），按主题归类即可，不必逐文件罗列。

**顺带检查本地调试残留**：写死的本地地址、打开的调试开关、注释掉的线上配置等，这类改动往往不该提交也不该写进周报正文，应单独提醒用户。
