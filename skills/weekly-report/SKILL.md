# Weekly Report — 从 git 变更反推工作周报

把一周的 git 变更提炼成一份人话周报。核心难点是**提交记录往往不可信**：消息写「其他一些优化」的提交可能混装十项改动，写「改名」的可能是一次架构重构。所以不能照着 `git log` 抄，必须读 diff 还原实际工作内容。

## 执行步骤

1. **确认时间范围**：默认本周一 00:00 至今天；用户指定则从用户（如"上周"、"最近三天"）。
2. **收集已提交变更** → `references/collection.md`：拿到提交清单，以及每条提交的文件数与增删行数。
3. **核对消息与改动是否匹配** → `references/collection.md` 的判断清单。命中可疑特征的提交**必须读 diff**，不要靠消息猜。
4. **收集未提交变更**：工作区与暂存区的改动同样算本周工作，按主题归类。
5. **成文** → `references/report-style.md`：按风格规范组织条目。
6. **落盘**：写入项目内 `docs/weekly-report-YYYY-MM-DD.md`（日期取时间范围最后一天）。若项目无 `docs/` 或另有惯例，跟随项目惯例并向用户说明位置。
7. **正文外提醒**：把不应写进周报但用户需要知道的事（未提交改动的提交计划、误留在代码里的本地调试配置等）放在文件末尾备注或对话中单独说明。

## 红线

1. **只写做出来的事，不写打算做的事**：未提交但已完成的改动可以计入，并注明尚未提交。
2. **不确定的不写**：看不出意图的改动宁可略过，也不要编造动机。存疑内容在对话里问用户。
3. **重构成条时必须交代架构问题**：说清「原来什么样 → 导致什么问题 → 现在怎么解决」，否则重构条目没有信息量。
4. **不泄漏技术细节到正文**：文件名、函数名、API 名、字段名不进周报，除非用户要求。技术细节是推理依据，不是输出内容。
5. **不擅自提交代码**：本 skill 只读 git 历史与 diff，不执行 `git commit`、`git add`、`checkout` 等写操作。
