# 各领域使用约束与红线

> 这是发现型/浏览型 skill，不要陷入 API 细节或规范原文；以下约束聚焦于"怎么聪明地浏览信息"。
> 输出格式规范见 `references/output-format.md`。

---

## LLM 领域

- AI 领域传闻多、发布会营销话术多，**见到 benchmark 数字先看测试集、评测条件**，警惕选择性披露。
- 官方博客与第三方解读之间，**以官方版本为准**。

## AI Agent 领域

- Agent 框架迭代极快，关注 **GitHub star 趋势、最近 commit 日期、issue 活跃度**，避免关注已冻结的项目。
- 协议类（MCP/A2A）关注 **spec 版本号和采纳进展**（草案/稳定/废弃），不必深究实现细节。
- 框架之间拿来对比时，分清**官方定位 vs 社区吹捧**，以官方发布为准。

## 前端开发领域

- 博客/教程常用旧版语法，**关注发布日期**，超过一年的前端文章优先看评论区是否有"已过时"提示。
- 浏览器新特性关注 **Chrome/Firefox/Safari 的发布渠道** 确认支持状态，不要只看一篇转载文章就说"可以用"。
- 框架更新关注 **breaking change**，其他小版本无需深究。

## 国际局势领域

### 交叉验证流程（强制执行）

1. 同一事件至少在 **两个相互独立的信源** 出现后再采信。
2. 区分「事实陈述」与「分析/评论」，评论不作事实用。
3. 标注事件发生时间与报道时间，避免把旧事当新闻。
4. 数字/伤亡范围等敏感信息，以**官方通报或多家通讯社一致口径**为准，单源不下结论。

### 红线

- **不把社交媒体帖文**（X/TikTok/Telegram 等）当作事实来源，只能当作「线索」，事实必须落到通讯社/官方/权威媒体。
- 涉及冲突、灾难、数字争议时，**默认存疑、交叉验证、标注时效**，宁可慢一步也不要传播未核实信息。
